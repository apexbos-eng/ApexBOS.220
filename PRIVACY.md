## 1. Overview & Core Privacy Commitment

ApexBOS.220 is an open-source, experimental radio frequency (RF) telemetry research and layout visualization tool designed for amateur railway enthusiasts and radio experimenters.

**Neither the current version of the software nor its developers collect, store, transmit, sell, or monitor any personal identifying information (PII).**

Privacy and local user sovereignty are fundamental architectural principles of this project:
- **No Telemetry or Analytics:** The software contains no tracking beacons, usage telemetry, analytics hooks, crash-reporting daemons, advertising identifiers, or user surveillance mechanisms.
- **No Central Account System:** The application does not require, prompt for, or manage user accounts, logins, usernames, passwords, or personal profiles.
- **No Phone-Home Architecture:** The core software does not communicate with any developer server, phone-home service, or external metric aggregator during runtime.

## 2. Information Handled by the Application

### 2.1 Over-the-Air Radio Frequency (RF) Data
The software interfaces with software-defined radio (SDR) hardware (e.g., RTL-SDR, Airspy, HackRF) to receive publicly broadcast radio frequency transmissions on the 220–222 MHz band. These signals:
- Originate from publicly transmitting trackside and locomotive radio transceivers.
- Are processed locally in volatile system memory (RAM) for demodulation, bit synchronization, and protocol decoding.
- Contain equipment status telemetry (e.g., signal aspects, switch positions, mileposts, locomotive IDs); they do not contain personal identifying information of software users.

### 2.2 Local Configuration & State Files
The software generates and maintains local configuration files strictly on your host machine:
- **Settings & Defaults:** Files such as `config.json`, `config.defaults.json`, and component-specific configuration files store local device preferences (SDR gain, PPM correction, monitored channel lists, and local network port numbers).
- **Layout & Preferences:** Layout definition files (`layouts/*.json`) and user display preferences (`prefs_*.json`) store visual presentation settings, zoom levels, and track display geometries.
- **Authentication & Encryption Keys:** Symmetric encryption keys (Fernet) and authentication secrets (TOTP) generated during setup remain stored on your local disk. They are never transmitted to the developer or any central authority.
- **Diagnostic Logs:** Any optional log files generated by the application or background tasks are written solely to your local storage drive and remain entirely under your control.

### 2.3 Network Communication & Relays
When networking features are enabled:
- **Local Network / Multicast:** Modules such as Grabber, Flux, Engine, and Viewer communicate over local network loopback (`127.0.0.1`), local area network (LAN) interfaces, or user-specified UDP multicast groups (e.g., `224.1.1.1` or `239.1.1.1`).
- **Cloud Banc Relays:** If you deploy or connect to a remote Banc server, telemetry bursts are transmitted over an encrypted TCP connection using your configured Fernet key and TOTP credentials. This connection is strictly direct between your client node and the Banc server endpoint you configure; no data is routed through or visible to the developer or any third party.
- **Network Identity Hashing:** To keep whitelisted home-network identities stable across computers on the same LAN, clients locally compute a one-way 12-character SHA-256 hash of the local default gateway's MAC address (with local-only fallbacks). The raw router MAC address is never transmitted in plaintext, and no external IP/identity lookup service is contacted.

## 5. User Responsibility & Caution with Open-Source Applications

Users must exercise caution and sound security hygiene when downloading, installing, configuring, and running this or any other open-source software application.

### Recommended Safety & Security Practices:
1. **Verify Checksums & Origin:** Always obtain the software directly from the official project repository. Verify cryptographic hashes (SHA-256) of release archives before executing installers or updating binaries.
2. **Review Scripts Before Execution:** Inspect setup scripts (`setup.bat`, `setup.sh`, `setup_wizard.py`) and administrative scripts (`enable_firewall.bat`, `enable_firewall.ps1`) before executing them with elevated privileges.
3. **Network Boundary & Firewall Isolation:**
   - Do not expose unauthenticated ZMQ ports or local multicast groups to the untrusted public internet.
   - Use secure tunneling (such as WireGuard, OpenVPN, or SSH port forwarding) when accessing remote nodes.
   - When deploying Banc or Flux endpoints, always configure strong, unique authentication secrets and cryptographic keys.
4. **Hardware & Radio Safety:** Ensure that software-defined radio hardware is connected with appropriate antenna grounding and ESD protection. Do not attach SDR receivers to unauthorized transmitters or exceed recommended input power levels.
5. **Regulatory Compliance:** RF reception laws vary by jurisdiction. Users are solely responsible for ensuring that their radio reception, decoding, and monitoring activities comply with all applicable local, national, and international laws, regulations, and licensing requirements.
